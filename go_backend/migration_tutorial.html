فهم الهيكلية: NestJS مقابل Django

لفهم NestJS، أفضل طريقة هي مقارنتها بما تعرفه مسبقاً في Django. في جانغو، أنت تقسم مشروعك إلى تطبيقات (Apps) (مثل: users, accounting). في NestJS، المفهوم المقابل تماماً يسمى الوحدات (Modules).

مقارنة الملفات الأساسية داخل كل App / Module:

المسؤولية في Django في NestJS
استقبال الـ API (الروابط) views.py أو api.py *.controller.ts
المنطق والعمليات (Logic) services.py (إن وُجد) *.service.ts
قاعدة البيانات (الجداول) models.py schema.prisma (باستخدام Prisma)
تسجيل الـ App INSTALLED_APPS في Settings app.module.ts

مثال عملي: كيف تتعامل مع هذه الملفات الثلاثة؟

لتفهم كيف تترابط هذه الملفات، تخيل أن تطبيق فلاتر أرسل طلباً لجلب قائمة المستخدمين (GET /users). هكذا يكون تسلسل العمل:

1 الوحدة (users.module.ts)

دورها فقط أن تعرّف السيرفر بوجود الـ Controller والـ Service معاً. نادراً ما ستكتب كوداً معقداً هنا.

@Module({
  controllers: [UsersController],
  providers: [UsersService],
})
export class UsersModule {}

2 المتحكم (users.controller.ts)

هو "موظف الاستقبال". يحدد شكل الرابط (مثلاً @Get())، يستقبل الطلب، ولكنه لا يقوم بجلب البيانات بنفسه، بل يمرر المهمة إلى الـ Service.

@Controller('users')
export class UsersController {
  // نقوم بحقن (Inject) الـ Service هنا لاستخدامها
  constructor(private readonly usersService: UsersService) {}

  @Get() // تعني أن هذا الرابط يعمل بطلب GET
  getAllUsers() {
    return this.usersService.findAll(); // اطلب من الـ Service العمل
  }
}

3 الخدمة (users.service.ts)

هو "الطباخ". هنا نكتب كل الشغل الثقيل: الاتصال بقاعدة البيانات (Prisma)، الحسابات المعقدة، والمنطق الحقيقي، ثم يعيد النتيجة للـ Controller.

@Injectable()
export class UsersService {
  findAll() {
    // هنا لاحقاً سنستخدم Prisma لجلب البيانات من قاعدة البيانات
    return [
      { id: 1, name: 'Ahmed' },
      { id: 2, name: 'Ali' }
    ];
  }
}

مقدمة المشروع وقواعد العمل

هذا الملف يعتبر المرجع الأساسي والدليل التعليمي الخاص بك لمشروع SolarHub. سيتم تحديث هذا الملف برمجياً مع كل خطوة ننجزها، ليحتوي على شرح الأكواد، القرارات المعمارية، وكيفية توافق الكود الجديد مع كود جانغو القديم.

القواعد الصارمة التي نتبعها:

  • التطابق التام (Exact API Matching): أي مخرج API يجب أن يكون متطابقاً مع جانغو لكي لا نتعطل في تطبيق فلاتر.
  • مدير الحزم: نستخدم pnpm بدلاً من npm للسرعة وتوفير المساحة.
  • توثيق الشفرة: وضع تعليقات إنجليزية تشرح كل مكون جديد في NestJS وعلاقته بالكود القديم.
  • قاعدة البيانات: استخدام Prisma لقراءة الجداول القديمة دون المساس ببياناتها.

التوثيق التلقائي (Swagger & OpenAPI)

تماماً مثلما كان يفعل Django Ninja، تمتلك بيئة NestJS دعماً رسمياً وممتازاً لتوليد توثيق الـ API بشكل تلقائي باستخدام Swagger.

كل ما علينا فعله هو تثبيت حزمة @nestjs/swagger، وبمجرد كتابة الأنواع (Types) والـ (DTOs) في TypeScript، سيقوم NestJS تلقائياً بتوليد واجهة مستخدم (Swagger UI) جذابة يمكنك من خلالها تجربة الـ API، ويمكنك أيضاً تصدير ملف JSON جاهز ليتم استيراده بضغطة زر داخل Postman.

1

تأسيس بيئة NestJS

مكتمل

1. أمر إنشاء المشروع

لإنشاء المشروع نستخدم أداة @nestjs/cli ونحدد pnpm كمدير للحزم لضمان السرعة والتنظيم:

npx @nestjs/cli new solarhub-nestjs --package-manager pnpm

2. أوامر توليد الوحدات (Modules)

في NestJS، لا نكتب الملفات يدوياً من الصفر. نستخدم الـ CLI لتوليد الهيكلة الصحيحة. مثلاً، لتوليد تطبيق (Module) خاص بالمستخدمين:

# الدخول لمجلد المشروع
cd solarhub-nestjs

# توليد الوحدة (Module)
npx nest g module users

# توليد المتحكم (Controller) للروابط
npx nest g controller users

# توليد الخدمة (Service) للعمليات
npx nest g service users

ملاحظة: حرف g هو اختصار لكلمة generate.

3. وظيفة الملفات الأساسية المتولدة

بعد إنشاء المشروع، ستجد مجلد src بداخله الملفات التالية:

  • main.ts
    قلب التطبيق (Entry File): يقابل manage.py أو wsgi.py في جانغو. وظيفته تشغيل السيرفر على بورت معين (مثل 3000) وربط كل شيء.
  • app.module.ts
    الوحدة الرئيسية (Root Module): يقابل قائمة INSTALLED_APPS في settings.py. يتم فيه تسجيل جميع الوحدات الفرعية وقواعد البيانات.
  • app.controller.ts
    واجهة الروابط الافتراضية: يحتوي على رابط برمجي بسيط (غالباً يعيد كلمة Hello World) للتأكد من عمل السيرفر. يقابل urls.py / views.py.
  • app.service.ts
    الخدمة الافتراضية: تحتوي على الكود أو المنطق الذي يعيد الجملة للـ Controller.
2

إعداد قاعدة البيانات (Prisma ORM)

قيد التنفيذ

نحن لا نريد إنشاء الجداول من الصفر وفقدان البيانات القديمة. لذلك سنستخدم أداة Prisma التي ستقوم بالاتصال بقاعدة بيانات جانغو الحالية وتقرأ الجداول منها تلقائياً (عملية تسمى Introspection).

أوامر التثبيت:

# تأكد أنك داخل مجلد المشروع
cd solarhub-nestjs

# تثبيت Prisma
pnpm add -D prisma
pnpm add @prisma/client

# تهيئة Prisma مع اختيار SQLite كقاعدة بيانات
npx prisma init --datasource-provider sqlite

بعد تنفيذ هذه الأوامر، سيتولد مجلد prisma وملف .env. ستقوم بفتح ملف .env وتعديل رابط الاتصال ليؤشر على ملف db.sqlite3 الخاص بجانغو هكذا: 

DATABASE_URL="file:../../solar_hub/db.sqlite3"

أخيراً، قم بتشغيل هذا الأمر لسحب جميع الجداول القديمة من جانغو وتحويلها إلى كود NestJS تلقائياً: 

npx prisma db pull
npx prisma generate

نصيحة احترافية: الانتقال إلى MariaDB للإنتاج

بما أنك تستخدم SQLite في التطوير وستنتقل إلى MariaDB في الإنتاج، فإن Prisma يسهل عليك هذا جداً. عند الإطلاق للإنتاج، ستقوم بفتح ملف schema.prisma وتغيير provider = "sqlite" إلى provider = "mysql" (لأن MariaDB تتوافق مع محرك MySQL)، ثم تقوم بتغيير DATABASE_URL في ملف .env ليؤشر إلى سيرفر MariaDB. هذا كل شيء!

دليل Prisma لمطوري Django

بما أنك قادم من بيئة جانغو، فأنت معتاد على ملف models.py حيث تعرّف الجداول (Classes)، وتستخدم أوامر مثل makemigrations لتطبيقها، و Model.objects للاستعلام. هنا سنقارن كل ذلك بـ Prisma.

1. أين نكتب الجداول؟ (schema.prisma مقابل models.py)

في Prisma، لا يتم تشتيت الجداول في مجلدات (Apps) منفصلة، بل يتم كتابة جميع الجداول في ملف واحد مركزي هو prisma/schema.prisma. هذا يسهل رؤية العلاقات بشكل واضح جداً.

2. الدليل الشامل لأنواع البيانات (Data Types)

هذا الجدول يمثل مرجعك الشامل لتحويل أي حقل من جانغو إلى ما يقابله في Prisma:

حقل Django حقل Prisma ملاحظات هامة
النصوص والأرقام الأساسية
CharField / TextFieldStringلا داعي لتحديد max_length في Prisma غالباً.
IntegerFieldIntللأرقام الصحيحة.
BigAutoFieldBigInt (أو Int)يفضل استخدام Int لتجنب مشاكل JSON في NestJS.
FloatFieldFloatللأرقام العشرية.
DecimalFieldDecimalيستخدم للأسعار والأموال لضمان الدقة (تتطلب حزمة Decimal.js).
BooleanFieldBooleanيأخذ قيمة true أو false.
التاريخ والوقت (Dates)
DateTimeField / DateFieldDateTimeنوع واحد يشمل التاريخ والوقت معاً.
auto_now_add=True@default(now())يأخذ تاريخ الإنشاء تلقائياً.
auto_now=True@updatedAtيتحدث تلقائياً عند أي تعديل على السطر.
الصور والملفات (Files)
ImageField / FileFieldStringمهم جداً: Prisma ليست مسؤولة عن رفع الملفات. في قاعدة البيانات نكتفي بحفظ مسار أو رابط الصورة كنص (String). عملية الرفع تتم في Controller عبر مكتبة Multer.
الأنواع المعقدة والخيارات (Advanced)
JSONFieldJsonمدعوم في MySQL/MariaDB و Postgres لحفظ بيانات ديناميكية كـ JSON. (غير مدعوم في SQLite).
choices=...enum Role { ADMIN USER }في جانغو نستخدم choices، في Prisma نصنع enum مخصص ونستخدمه كنوع بيانات. (ملاحظة: Enums مدعومة في MariaDB ولكنها غير مدعومة في SQLite).
null=True, blank=Trueإضافة ? (مثال String?)يعني أن الحقل اختياري (Nullable).
default="..."@default("...")لإعطاء قيمة افتراضية للحقل.

3. المفاتيح، الفهارس، والقيود (Indexes & Constraints)

في Django في Prisma الوصف
primary_key=True@idيحدد المفتاح الأساسي للجدول (مثل: id Int @id @default(autoincrement())).
unique=True@uniqueيمنع التكرار لهذا الحقل (مثال: رقم الهاتف أو الإيميل).
db_index=True@@index([field])يُضاف في آخر الجدول لتسريع عملية البحث عن طريق هذا الحقل.
unique_together = [...]@@unique([field1, field2])يُضاف في آخر الجدول لمنع تكرار تركيبة من حقلين معاً.

4. مقارنة العلاقات (Relationships) التفصيلية

في جانغو، عندما تنشئ علاقة (Foreign Key)، يتم وضع الحقل في جدول واحد فقط. أما في Prisma، فإن العلاقة مرئية من الطرفين بشكل يسهل فهمه جداً.

علاقة 1 إلى متعدد (Django)
class User(models.Model):
    name = models.CharField(max_length=100)
    # لا يظهر هنا أن لديه مقالات

class Post(models.Model):
    title = models.CharField(max_length=100)
    user = models.ForeignKey(User, on_delete=models.CASCADE)
نفس العلاقة في Prisma
model User {
  id    Int    @id @default(autoincrement())
  name  String
  // العلاقة مرئية! المستخدم لديه مصفوفة مقالات
  posts Post[] 
}

model Post {
  id      Int    @id @default(autoincrement())
  title   String
  user_id Int
  // ربط المفتاح الأجنبي وتحديد سلوك الحذف
  user    User   @relation(fields: [user_id], references: [id], onDelete: Cascade)
}
كيف نصنع علاقة متعدد إلى متعدد (Many-to-Many)؟

في جانغو نستخدم ManyToManyField. في Prisma، ببساطة نضع مصفوفة [] في كلا الجدولين، وتقوم Prisma تلقائياً بإنشاء الجدول الوسيط المخفي لربطهما!

model Student {
  id      Int      @id @default(autoincrement())
  courses Course[] // مصفوفة دورات
}

model Course {
  id       Int       @id @default(autoincrement())
  students Student[] // مصفوفة طلاب
}

5. مقارنة الاستعلامات (Queries)

استعلامات Prisma تتميز بأنها Type-Safe، يعني أن المحرر (VSCode) سيعرف تماماً ما هي الحقول الموجودة في النتيجة ويكملها لك تلقائياً ولن يسمح لك بكتابة اسم حقل خاطئ.

في Django (ORM)
# جلب كل المستخدمين
User.objects.all()

# جلب مستخدم واحد
User.objects.get(id=1)

# إنشاء مستخدم جديد
User.objects.create(name="Ali")
في Prisma
// جلب كل المستخدمين
await prisma.user.findMany()

// جلب مستخدم واحد
await prisma.user.findUnique({ where: { id: 1 } })

// إنشاء مستخدم جديد
await prisma.user.create({ data: { name: "Ali" } })

6. تطبيق التعديلات (Migrations)

في جانغو كنت تستخدم أمرين لتطبيق التعديلات على الجداول: makemigrations لصنع الملف، ثم migrate لتطبيقه.

في Prisma، بعد أن تعدل ملف schema.prisma (مثلاً أضفت حقلاً جديداً)، تنفذ أمراً واحداً يجمع الإثنين معاً:

npx prisma migrate dev --name init

هذا الأمر يقوم بـ:

  • إنشاء ملف SQL (مثل makemigrations).
  • تطبيق التعديلات على قاعدة البيانات (مثل migrate).
  • تحديث أنواع TypeScript فوراً لكي تظهر الحقول الجديدة في الكود (عبر أمر generate ضمناً).

7. مثال شامل (Cheat Sheet) يجمع كل شيء

هذا نموذج مرجعي كامل يمكنك نسخه والرجوع إليه دائماً لمعرفة طريقة كتابة أي حقل أو علاقة:

نموذج FullExample 
enum Role {
  ADMIN
  USER
  COMPANY
}

model FullExample {
  // المفتاح الأساسي (Primary Key)
  id            Int       @id @default(autoincrement())
  
  // النصوص الأساسية
  title         String    @unique // حقل فريد لا يتكرر (Unique)
  description   String?   // حقل اختياري يقبل Null (Nullable)
  
  // الأرقام
  views         Int       @default(0) // رقم صحيح مع قيمة افتراضية
  price         Decimal   // رقم للأسعار والأموال (يحافظ على الدقة)
  rating        Float?    // رقم عشري اختياري
  
  // القيم المنطقية (Boolean)
  is_published  Boolean   @default(false)
  
  // القوائم والـ JSON والأنواع المخصصة
  metadata      Json?     // لحفظ تفاصيل متغيرة (يعمل في MariaDB)
  role          Role      @default(USER) // استخدام نوع Enum
  
  // التواريخ والأوقات
  created_at    DateTime  @default(now()) // يأخذ تاريخ الإنشاء (auto_now_add)
  updated_at    DateTime  @updatedAt      // يتحدث مع كل تعديل (auto_now)
  
  // العلاقات: واحد إلى متعدد (One-to-Many)
  author_id     Int
  author        User      @relation(fields: [author_id], references: [id], onDelete: Cascade)
  
  // العلاقات: متعدد إلى متعدد (Many-to-Many)
  tags          Tag[]     // مجرد تعريف مصفوفة هنا وفي جدول Tag
  
  // الفهارس والقيود (Indexes & Constraints)
  @@index([author_id])             // لتسريع البحث عن طريق المؤلف (db_index)
  @@unique([title, author_id])     // يمنع تكرار العنوان لنفس المؤلف (unique_together)
}

هيكلية التوثيق والمستخدمين (Auth & Users)

1. دمج User و Profile (وداعاً للتعقيد!)

في جانغو، كنت مجبراً على استخدام جدول User الافتراضي الخاص بجانغو الذي يحتوي على حقول محددة. ولأنك لا تستطيع التعديل عليه بسهولة لإضافة حقول مخصصة (مثل الصورة، العنوان، وغيرها)، كنت تضطر لإنشاء جدول Profile وربطه بعلاقة One-to-One. هذا كان يسبب تعقيداً في الاستعلامات وبطئاً (استعلام مزدوج في كل مرة تريد جلب بيانات المستخدم).

في NestJS و Prisma: أنت المتحكم الوحيد!

بما أننا نبني النظام من الصفر هنا، لا يوجد جدول افتراضي يفرضه علينا إطار العمل. لذلك، القاعدة الذهبية هي: ادمج كل شيء في جدول User واحد!

نضع فيه الايميل، الباسورد، الصورة الشخصية، رقم الهاتف، وأي تفاصيل أخرى. هذا يجعل قاعدة البيانات أنظف بكثير واستعلاماتها أسرع بشكل ملحوظ لأنك لست بحاجة لعمل JOIN أو include لجلب تفاصيل الـ Profile أبداً.

2. كيف يعمل تسجيل الدخول (Authentication)؟

جانغو كان يستخدم (Session/Cookies) افتراضياً أو (Token Authentication) مع DRF. في NestJS، المعيار الصناعي الحديث لتطبيقات الموبايل (Flutter) والويب هو استخدام JWT (JSON Web Tokens). هكذا دورة حياة التوثيق:

1

إنشاء التوكن (Login)

عندما يرسل المستخدم إيميله والباسورد لـ AuthController، نقوم بالتحقق منها. إذا كانت صحيحة، نستخدم حزمة @nestjs/jwt لتوليد Token مشفر (يحتوي بداخله على الـ id الخاص به) ونرسله لتطبيق فلاتر ليحفظه عنده.

2

حماية المسارات (AuthGuard)

في جانغو كنا نكتب @login_required أو permission_classes=[IsAuthenticated]. في NestJS، نكتب @UseGuards(AuthGuard) فوق الـ Controller أو المسار. هذا الـ Guard هو "حارس أمن" يعترض أي طلب، يقرأ التوكن من الـ Authorization Header، يفك تشفيره، وإذا كان سليماً يسمح للطلب بالمرور.

3

معرفة المستخدم الحالي (Current User)

في جانغو كنت تستخدم request.user للوصول لبيانات صاحب الطلب. في NestJS، سنصنع أداة مخصصة (Custom Decorator) اسمها @CurrentUser() نضعها كمعامل في الدالة داخل الـ Controller لتسحب بيانات المستخدم فورا، مثلاً: getProfile(@CurrentUser() user: User).

3. ميزة رائعة: إخفاء كلمة المرور تلقائياً

في قاعدة البيانات، سنقوم بتشفير كلمات المرور باستخدام bcrypt (تماما كما يفعل جانغو). لكن في Prisma، لا نريد أبداً أن تعود كلمة المرور المشفرة بالخطأ عند جلب بيانات المستخدم وإرسالها لـ API لكي لا يراها المخترقون. لذلك، سنتعلم كيفية عمل (Interceptor) أو تعديل إعدادات Prisma لكي تقوم بحذف حقل password تلقائياً من أي استعلام findMany أو findUnique قبل إرسال النتيجة للـ Controller.

الدرس الأول: تحويل نظام Users & Auth بالكامل (من الألف إلى الياء)

مرحباً بك يا صديقي في أول درس عملي واحترافي! بصفتي المدرس الخاص بك، قمت بتحليل دقيق لملف users/api.py القديم الخاص بك في جانغو. كان لديك 12 مساراً (Endpoint) رئيسياً (Login, Register, Profile, etc). اليوم سنتعلم كيف نحولها إلى NestJS بأعلى معايير الصناعة.

1. المعمارية: كيف تختلف عن Django Ninja؟

في Django Ninja كنت تكتب: Schema ثم @router.post وتضع اللوجيك داخل الـ View. في NestJS نقسم العمل كالتالي:

  • DTOs بديل الـ (Schema). مسؤولة عن التحقق من صحة البيانات القادمة (Validation).
  • Service هنا نكتب اللوجيك الصعب (مثل User.objects.create() و التشفير).
  • Controller بديل الـ (Router). يستقبل الطلب، يرسله للـ Service، ثم يرجع النتيجة للعميل (Flutter).

2. حزم أساسية يجب تثبيتها أولاً

جانغو كان يأتي جاهزاً بالتشفير ونظام المستخدمين. في NestJS، نحن نركب الأدوات التي نريدها بحرية:

pnpm add bcrypt @nestjs/jwt class-validator class-transformer
pnpm add -D @types/bcrypt
  • bcrypt: لتشفير كلمات المرور والتحقق منها (بديل make_password و check_password).
  • @nestjs/jwt: لتوليد التوكن (بديل مكتبة jwt التي كنت تستخدمها).
  • class-validator: للتحقق من المدخلات (مثل التأكد أن الإيميل صحيح).

3. توليد الـ Module

لإنشاء التطبيق بالكامل بضغطة زر، نفذ هذا الأمر:

pnpm exec nest g resource auth

(اختر REST API، وسيسألك إذا كنت تريد توليد CRUD، اختر No لأننا سنكتب الـ Endpoints بأنفسنا).

4. بناء الـ DTO (بديل LoginSchema و RegisterSchema)

في جانغو كنت تكتب: class LoginSchema(Schema): username: str. في NestJS سنصنع ملف auth/dto/login.dto.ts:

import { IsString, IsNotEmpty, MinLength } from 'class-validator';

export class LoginDto {
  @IsString()
  @IsNotEmpty({ message: 'اسم المستخدم مطلوب' })
  username: string;

  @IsString()
  @MinLength(6, { message: 'كلمة المرور يجب أن تكون 6 أحرف على الأقل' })
  password: string;
}

💡 تلميح المحترفين: في NestJS، لكي تعمل هذه الشروط تلقائياً وترفض الطلبات الخاطئة قبل أن تصل للـ Controller، يجب تفعيل ValidationPipe عالمياً في ملف main.ts.

5. بناء الـ Service (اللوجيك الحقيقي)

في جانغو، دالة api_login كانت تستخدم authenticate(). هنا سنبنيها خطوة بخطوة في auth.service.ts:

import { Injectable, UnauthorizedException, BadRequestException } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';
import * as bcrypt from 'bcrypt';
import { JwtService } from '@nestjs/jwt';
import { LoginDto } from './dto/login.dto';

const prisma = new PrismaClient(); // (يفضل عمل PrismaService مخصص لاحقاً)

@Injectable()
export class AuthService {
  constructor(private jwtService: JwtService) {}

  async login(data: LoginDto) {
    // 1. البحث عن المستخدم (بديل User.objects.filter)
    const user = await prisma.user.findUnique({
      where: { username: data.username }
    });

    // 2. التحقق من المستخدم وكلمة المرور
    if (!user || user.is_deleted || !user.is_active) {
      throw new UnauthorizedException('الحساب غير موجود أو تم إيقافه.');
    }

    const isPasswordValid = await bcrypt.compare(data.password, user.password);
    if (!isPasswordValid) {
      throw new UnauthorizedException('كلمة المرور غير صحيحة.');
    }

    // 3. توليد التوكن
    const token = this.jwtService.sign({ id: user.id, username: user.username });

    // 4. حذف كلمة المرور من النتيجة قبل إرجاعها (مهم أمنياً!)
    const { password, ...userWithoutPassword } = user;

    return {
      message: "Login successful",
      token,
      user: userWithoutPassword
    };
  }
}

6. بناء الـ Controller (الروابط)

في جانغو كنت تكتب @router.post("/login"). في NestJS نكتبها في auth.controller.ts:

import { Controller, Post, Body } from '@nestjs/common';
import { AuthService } from './auth.service';
import { LoginDto } from './dto/login.dto';
import { RegisterDto } from './dto/register.dto';

@Controller('auth') // هذا يعني أن المسار يبدأ بـ /auth
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Post('login') // المسار النهائي: /auth/login
  async login(@Body() body: LoginDto) {
    return this.authService.login(body);
  }

  @Post('register')
  async register(@Body() body: RegisterDto) {
    return this.authService.register(body);
  }
}

7. بديل json_response و الأخطاء (Exception Handling)

في جانغو كنت تستخدم دالة مخصصة json_response(status=400, error=True).

في NestJS، إذا أردت إرجاع خطأ، فقط قم برمي استثناء (Throw Exception) وNestJS سيتكفل بتحويله إلى JSON نظيف لتطبيق Flutter:

  • throw new BadRequestException('Email already exists'); (يرجع Status 400)
  • throw new NotFoundException('User not found'); (يرجع Status 404)
  • throw new UnauthorizedException('Wrong password'); (يرجع Status 401)

وإذا أردت توحيد شكل الاستجابة (مثلاً أن تكون دائماً { data, message, error })، يمكنك لاحقاً بناء Interceptor و Exception Filter ليقوم بتغليف كل الردود بهذا الشكل تلقائياً دون أن تكتبه في كل دالة!

8. التعامل مع الحماية (Guards) بدلاً من AuthBearer

في الـ api.py الخاص بك كان لديك: @router.get("/profile", auth=AuthBearer()).

في NestJS، ستقوم بإنشاء كلاس اسمه JwtAuthGuard (يتحقق من التوكن)، وتضعه فوق المسار هكذا:

import { UseGuards, Get } from '@nestjs/common';
import { JwtAuthGuard } from './jwt-auth.guard'; // سنقوم بإنشائه لاحقاً

@UseGuards(JwtAuthGuard)
@Get('profile')
async getProfile(@Request() req) {
  // req.user يحتوي على بيانات المستخدم المستخرجة من التوكن
  return req.user; 
}

🎯 خلاصة الدرس الأول للمحترفين

  1. افصل اللوجيك: لا تكتب أكواد قواعد البيانات (Prisma) داخل الـ Controller أبداً. ضعها دائماً في الـ Service.
  2. استخدم الـ DTOs دائماً: لا تستقبل أي @Body() بدون DTO قوي محمي بـ class-validator.
  3. كلمات المرور: لا تنسَ تشفير كلمة المرور بـ bcrypt.hash() في مسار الـ Register، ولا ترجعها أبداً في الـ Response.
  4. الـ JWT: قم بتخزين JWT_SECRET في ملف .env ولا تضعه في الكود مباشرة.

الدرس الثاني: توثيق الـ APIs باستخدام Swagger 📝

في Django Ninja، كان توثيق Swagger يُبنى تلقائياً بمجرد كتابة الـ Schema. في NestJS، الأمر مشابه جداً وقوي للغاية، لكنه يحتاج إلى تفعيل مبدئي وبعض اللمسات البسيطة ليكون احترافياً.

1. تثبيت حزمة Swagger

أول خطوة هي تثبيت الحزمة الرسمية الخاصة بـ NestJS:

pnpm add @nestjs/swagger

2. تفعيل Swagger في ملف main.ts

لكي تعمل واجهة التوثيق، يجب إعدادها في ملف نقطة البداية src/main.ts قبل سطر app.listen():

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { SwaggerModule, DocumentBuilder } from '@nestjs/swagger';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // === إعدادات Swagger ===
  const config = new DocumentBuilder()
    .setTitle('Watt API') // عنوان التوثيق
    .setDescription('The SolarHub Backend API description') // وصف بسيط
    .setVersion('1.0') // الإصدار
    .addBearerAuth() // 👈 هذه مهمة جداً لكي يظهر زر إدخال التوكن (JWT) في الواجهة!
    .build();
    
  const document = SwaggerModule.createDocument(app, config);
  
  // تحديد الرابط الذي سيفتح عليه التوثيق (هنا سيكون: localhost:3000/api-docs)
  SwaggerModule.setup('api-docs', app, document);
  // ========================

  await app.listen(3000);
}
bootstrap();

بعد ذلك، بمجرد تشغيل السيرفر، ستتمكن من تصفح التوثيق عبر الرابط: http://localhost:3000/api-docs

3. كيف توثق المدخلات (DTOs) لكي تظهر في Swagger؟

في ملفات الـ DTO (مثل login.dto.ts)، يجب أن تخبر Swagger عن كل حقل باستخدام مزخرف @ApiProperty() لكي يعرف كيف يعرضه للمبرمجين الآخرين أو لتطبيق فلاتر:

import { ApiProperty } from '@nestjs/swagger';
import { IsString, IsNotEmpty } from 'class-validator';

export class LoginDto {
  @ApiProperty({
    description: 'اسم المستخدم للعميل',
    example: 'ali_ahmed' // مثال يظهر تلقائياً في التوثيق
  })
  @IsString()
  @IsNotEmpty()
  username: string;

  @ApiProperty({
    description: 'كلمة المرور',
    example: 'password123',
    minLength: 6
  })
  @IsString()
  password: string;
}

الدرس الثالث: توحيد مخرجات الـ API (Interceptors & Filters) 🌐

في تطبيقك القديم على Django، كان لديك شكل ثابت وموحد لكل رد يخرج من السيرفر لتطبيق Flutter، وكان يأخذ هذا الشكل:

{
  "status": 200,
  "message": "Success",
  "body": { ... },
  "error": false,
  "message_user": null
}

في Django كنت تكتب دوال مثل json_response() وتستخدمها في كل مسار. في NestJS، نحن نعتمد على أدوات أكثر احترافية وذكاءً لا تتطلب منك تغيير الكود في كل Controllers الخاص بك. هذه الأدوات هي Interceptors للحالات الناجحة، و Exception Filters لحالات الخطأ.

1. التعامل مع الاستجابات الناجحة (Response Interceptor)

الـ Interceptor هو كود يتدخل (يعترض) الرد القادم من الـ Controller قبل أن يتم إرساله إلى العميل (Flutter). هنا نقوم بتغليف البيانات بالشكل الموحد المطلوب:

import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common';
import { Observable } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable()
export class ResponseInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable {
    const ctx = context.switchToHttp();
    const response = ctx.getResponse();

    return next.handle().pipe(
      map(data => {
        // إذا كان المطور قد أرجع رسالة مخصصة مع البيانات
        const message = data?.message || 'Success';
        const body = data?.message ? (data.user || data.data || data) : data;

        return {
          status: response.statusCode,
          message: message,
          body: body,
          error: false,
          message_user: null,
        };
      }),
    );
  }
}

2. التعامل مع الأخطاء والاستثناءات (Exception Filter)

الـ Exception Filter يتدخل فقط عندما يتم رمي خطأ أو استثناء في السيرفر (مثلاً عندما يضعف المطور كلمة المرور أو يخطئ في كتابة الإيميل). هذا يضمن أن تطبيق فلاتر سيتلقى نفس الهيكلية حتى عند حدوث مشكلة:

import { ExceptionFilter, Catch, ArgumentsHost, HttpException, HttpStatus } from '@nestjs/common';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    
    let status = HttpStatus.INTERNAL_SERVER_ERROR;
    let message = 'Internal server error';

    if (exception instanceof HttpException) {
      status = exception.getStatus();
      const res = exception.getResponse();
      message = typeof res === 'string' ? res : (res as any).message || res;
    } else if (exception instanceof Error) {
      message = exception.message;
    }

    response.status(status).json({
      status: status,
      message: Array.isArray(message) ? message[0] : message, // تجنب مصفوفة الرسائل
      body: null,
      error: true,
      message_user: null,
    });
  }
}

3. تفعيل هذه الأدوات لتعمل عالمياً (Globally)

لكي لا تضطر لإضافة هذه الأدوات في كل مسار أو Module، نذهب إلى ملف main.ts ونخبر NestJS بأن هذه القاعدة تطبق على المشروع كاملاً:

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';
import { ResponseInterceptor } from './common/interceptors/response.interceptor';
import { AllExceptionsFilter } from './common/filters/all-exceptions.filter';
import { ValidationPipe } from '@nestjs/common';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // تفعيل الـ Interceptor للاستجابات الناجحة
  app.useGlobalInterceptors(new ResponseInterceptor());
  
  // تفعيل الـ Filter لرسائل الخطأ
  app.useGlobalFilters(new AllExceptionsFilter());
  
  // تفعيل الـ ValidationPipe لضمان تحقق الـ DTOs تلقائياً
  app.useGlobalPipes(new ValidationPipe({ whitelist: true }));

  await app.listen(3000);
}
bootstrap();

🎯 خلاصة الدرس الثالث

بهذا الإعداد الاحترافي، لا داعي للتفكير في شكل الاستجابة بعد الآن! في أي مسار أو Controller جديد، كل ما عليك فعله هو إرجاع البيانات return user; وسيتكفل NestJS بتغليفها بـ {"status": 200, "message": "Success", "body": { ... }} تلقائياً.

وعندما تريد إرجاع خطأ، فقط اكتب throw new BadRequestException('كلمة المرور ضعيفة') وسيتكفل NestJS بتحويلها إلى شكل JSON موحد لتطبيق فلاتر.

الدرس الرابع: توثيق المستخدمين (Auth & Users) 🔐

تطبيق المستخدمين (Users App) كان يحتوي على العديد من الوظائف في Django، وقد نقلناها جميعاً إلى وحدة AuthModule في NestJS مع الالتزام التام بكيفية عملها سابقاً للحفاظ على توافق تطبيق فلاتر.

1. تسجيل الدخول وتسجيل حساب جديد

في دالة تسجيل الدخول (Login)، قمنا ببناء الميزة بحيث تسمح بتسجيل الدخول باستخدام (الإيميل، رقم الهاتف، أو اسم المستخدم) بفضل دالة مساعدة تبحث عن المستخدم:

private async findUserByIdentifier(identifier: string) {

      OR: [

@Post('password-reset')
async requestPasswordReset(@Body() body: PasswordResetRequestDto) {
  // يقوم بالبحث باستخدام الإيميل، رقم الهاتف، أو اسم المستخدم
  // ثم يرسل الكود المكون من أرقام للبريد المرتبط
}

3. صورة المستخدم (Avatar) والصيغة الثابتة

بناءً على التوجيهات، قمنا بتوحيد شكل الملف الشخصي (Profile) عند إرجاعه بحيث يكون مطابقاً لمخرجات جانغو، مع إرجاع image: null دائماً لأنه تقرر حذف الصورة الشخصية من المستخدمين والاعتماد على صورة افتراضية في الواجهات:

private serializeUser(user: any) {
  return {
    id: user.id,
    username: user.username,

    first_name: user.first_name,
    last_name: user.last_name,
    phone: user.phone,
    city: user.city ? { id: user.city.id, name: user.city.name } : null,

✅ ملخص الميزات المكتملة في Auth Module

  • تسجيل الدخول والتسجيل بنجاح وإنشاء JWT Token.
  • جلب وتحديث بيانات المستخدم /auth/profile.
  • ترقية مستخدم لمدير /auth/promote (محمية بصلاحيات Superuser).
  • حذف الحساب مؤقتاً (Soft Delete) باستخدام is_deleted.
  • تغيير وتأكيد كلمة المرور بالتوكن الرقمي /auth/password-reset/confirm.
  • تغيير لغة المستخدم بين 'ar' و 'en' فقط /auth/language.

الدرس الخامس: لوحة التحكم (Admin Site) وصلاحيات الـ Superuser 👑

من أهم ميزات إدارة النظام في Django هو أمر createsuperuser لإنشاء مدير جديد بصلاحيات كاملة للتحكم بالنظام. لقد قمنا بتعويض هذه الميزة باحترافية في NestJS.

إنشاء أمر createsuperuser (Command Line Interface)

في تطبيقنا الجديد، قمنا بكتابة ملف سكريبت منفصل في src/scripts/create-superuser.ts يتصل بقاعدة البيانات بشكل مباشر عبر Prisma ويسألك عن بياناتك.

لتبسيط استخدامه، أضفنا هذا الاختصار في ملف package.json:

"scripts": {
  "createsuperuser": "ts-node -r tsconfig-paths/register src/scripts/create-superuser.ts"
}

الآن لإنشاء حساب مدير بصلاحيات كاملة، كل ما عليك فعله هو كتابة هذا الأمر في الشاشة السوداء (Terminal):

pnpm run createsuperuser

السكريبت سيطلب منك إدخال:

  • اسم المستخدم (Username)
  • البريد الإلكتروني (Email)
  • كلمة المرور (Password)

وسيقوم بتشفير كلمة المرور بـ bcrypt وحفظ حسابك بصلاحيات is_superuser = true ليكون جاهزاً لإدارة النظام. يمكنك لاحقاً استخدام هذا الحساب لتسجيل الدخول إلى أي لوحة تحكم مخصصة يتم بناؤها.

الدرس السادس: لوحة التحكم المتقدمة باستخدام Refine 🚀

في نظام Django القديم، كانت لوحة التحكم (Admin Panel) جزءاً مدمجاً من كود الباك‌اند. أما الآن، فنحن نتبع المعايير الحديثة (Decoupled Architecture) بفصل الواجهة الأمامية تماماً.

1. إطار عمل Refine

لقد اخترنا إطار Refine (المبني على React) لبناء لوحة التحكم. لماذا؟ لأنه مصمم خصيصاً لبناء الأنظمة الداخلية (Internal Tools) ولوحات التحكم بسرعة هائلة، ويدعم الربط المباشر مع واجهات REST API.

2. الهيكلية الجديدة للمشروع

المشروع الآن مقسم إلى مجلدين رئيسيين جنباً إلى جنب:

  • solarhub-nestjs هذا هو السيرفر الأساسي. يعمل كـ API لخدمة تطبيق فلاتر ولوحة التحكم.
  • solarhub-admin هذا هو مجلد لوحة التحكم. تطبيق React مستقل يتخاطب مع الباك‌اند لجلب وعرض البيانات.

3. كيف يعملان معاً؟

في مرحلة التطوير، تقوم بتشغيل السيرفرين في وقت واحد (مثلاً: NestJS على المنفذ 3000 و Refine على 5173). يقوم تطبيق Refine بإرسال طلبات الـ HTTP إلى localhost:3000/api.

أما في مرحلة الإنتاج (Production)، يتم عمل build لمشروع Refine وتحويله إلى ملفات ثابتة (Static Files)، ثم نقوم ببرمجة NestJS ليقوم بعرض هذه الملفات على الرابط /admin، بحيث يعود النظام ليعمل من سيرفر واحد تماماً كما كان يفعل Django!

الدرس السابع: هجرة الشركات والإشعارات (Companies & Notifications) 🏢

من أهم خطوات التحديث هو نقل الوحدات المعقدة التي تحتوي على العديد من مسارات الـ API مثل الشركات (Companies) وخدمة الإشعارات (Firebase Admin) من بيئة جانغو إلى بيئة NestJS مع الحفاظ على نفس مخرجات الـ API تماماً.

1. وحدة الإشعارات (Notifications Module)

في تطبيق جانغو، كنا نعتمد على fcm-django لتخزين توكنات الأجهزة وإرسال الإشعارات. في NestJS:

  • تم استخدام مكتبة firebase-admin مباشرة وتهيئتها داخل NotificationsService.
  • تم ربط الجداول القديمة الخاصة بـ FCMDevice و NotificationMsg باستخدام Prisma.
  • قمنا بتقسيم الـ Controllers بحيث يكون لدينا DeviceController لإدارة أجهزة المستخدمين و AdminNotificationController لإرسال الإشعارات الجماعية بصلاحيات الـ Superuser.

2. وحدة الشركات (Companies Module)

تطبيق الشركات في جانغو كان يحتوي على ملف api.py عملاق يضم حوالي 2000 سطر برمجي. لترتيب هذا الكود في NestJS:

  • تقسيم المتحكمات: قمنا بإنشاء 7 متحكمات منفصلة في مجلد controllers (مثل CompaniesController، PublicCompaniesController، CompanyMembersController وغيرها) ليسهل صيانتها.
  • توحيد البيانات (DTOs): قمنا بإنشاء جميع كلاسات class-validator (الـ DTOs) لتكون مطابقة تماماً للـ Schemas القديمة في جانغو.
  • معالجة العلاقات المعقدة في Prisma: تم تحويل عمليات الإنشاء والتحديث، مثل إضافة CompanyMember وتحديد التواريخ الافتراضية مثل expire_date إلى كود Type-Safe في خدمة CompaniesService.

الدرس الثامن: العروض والمناقصات (Offers) 📝

تعتبر وحدة العروض OffersModule من أعقد الوحدات لأنها تربط المستخدمين بالشركات، وتحتوي على العديد من العمليات المتداخلة (طلبات العروض، الرد عليها، واختيار بنود العرض).

كيف نقلنا وحدة العروض إلى NestJS؟

  • تقسيم الـ Controllers: قمنا بإنشاء 4 متحكمات لتبسيط الكود:
    • UserOfferRequestsController: لطلبات المستخدمين.
    • CompanyOffersController: لردود الشركات على الطلبات.
    • InvolvementTemplatesController: لإدارة كتالوج البنود الإضافية للشركات.
    • AdminOffersController: للوحة التحكم الإدارية.
  • العلاقات مع قاعدة البيانات: تم استخدام Prisma للربط التلقائي وتوليد (Snapshot) لبنود العرض في OfferInvolvement و OfferInvolves.
  • التكامل مع الـ CRM (Customer): عند تقديم شركة لعرض، يتم تلقائياً تحويل المستخدم إلى Lead ضمن قاعدة عملاء الشركة (Customer) بنفس آلية جانغو.
  • الإشعارات (Notifications): تم ربط الخدمة بنظام الإشعارات المدمج لإرسال تنبيهات لحظية لكل من المستخدمين والشركات عند تفاعلهم.

الدرس التاسع: تهجير قسم المتجر (Shop) المعقد والفصل المنطقي

المشكلة في الكود القديم:

في مشروع جانغو القديم، كان قسم الـ Shop يجمع كل شيء في ملفين ضخمين (`commerce_api.py` و `product_api.py`). هذه الملفات كانت تدير الكتالوج العام، منتجات الشركات، طلبات B2B، طلبات B2C، العملاء، والموردين دفعة واحدة. هذا التصميم يجعل الصيانة وتتبع الأخطاء أو إضافة ميزات جديدة أمراً بالغ الصعوبة.

الحل في NestJS:

قررنا تطبيق مبدأ الفصل المنطقي (Separation of Concerns) وتقسيم قسم الـ Shop إلى 8 متحكمات (Controllers) منفصلة، كل منها يتعامل مع جزء محدد:

  • store-catalog.controller.ts: الكتالوج العام (للمشترين الأفراد B2C).
  • b2b-catalog.controller.ts: كتالوج الشركات (B2B).
  • company-products.controller.ts: إدارة الشركة لمنتجاتها.
  • company-customers.controller.ts: نظام الـ CRM للعملاء.
  • company-suppliers.controller.ts: نظام الـ CRM للموردين.
  • company-orders.controller.ts: إدارة مبيعات الشركة (الطلبات الواردة).
  • user-orders.controller.ts: إدارة مشتريات المستخدم (الطلبات الصادرة).
  • admin-products.controller.ts: لوحة تحكم الإدارة.

الدرس المستفاد:

أهمية استخدام سكريبتات التوليد (Code Generation):

لأن قسم الـ Shop يحتوي على أكثر من 40 مسار (Endpoint)، فإن كتابة كل هذه المتحكمات والخدمات (Services) يدوياً كان سيستغرق أياماً وسيكون عرضة للخطأ البشري (مثل نسيان `@ApiBearerAuth()` الذي حدث معنا سابقاً). قمنا بكتابة سكريبتات Python لإنشاء جميع ملفات الـ Shop دفعة واحدة. هذا يضمن لنا:

  • دقة 100% في تطبيق المزخرفات وحماية الروابط.
  • سرعة هائلة في تهجير الأقسام الضخمة.
  • أكواد نظيفة ومرتبة وفق قوالب موحدة.

الدرس العاشر: حماية الأدوار (RBAC) والفلاتر والإشعارات

التهجير النهائي لأقسام Offers و Shop:

بعد بناء الكود الأساسي، واجهتنا 3 تحديات ليكون الكود مطابقاً تماماً لـ Django:

  1. حماية الأدوار (CompanyMemberBearer): في جانغو كان هناك حماية قوية تتأكد من أن المستخدم ليس فقط مسجلاً الدخول، بل هو عضو في الشركة التي يحاول التحكم بها، ولديه دور (Role) محدد (مثلاً Manager). في NestJS، قمنا بإنشاء RolesGuard و مزخرف @Roles() يتفحص التوكن و company-id ويتأكد من الصلاحيات.
  2. الفلاتر والبحث في المتجر: متجر B2C و B2B يحتوي على فلاتر (min_price, max_price, category_id, q). قمنا بإنشاء ShopFiltersDto واستخدام منشئ استعلامات ديناميكي في Prisma لفلترة المنتجات والتقسيم لصفحات (Pagination). وأضفنا @ApiPropertyOptional لتظهر في Swagger.
  3. إشعارات Firebase (FCM): قمنا بنقل ملف fcm-service-account.json وتفعيل firebase-admin وبناء NotifierService ذكي يقرأ لغة المستخدم (عربي/إنجليزي) من قاعدة البيانات ويرسل الإشعار المترجم المناسب.

الدرس 11: التصدير وبناء التطبيق للرفع على VPS

بعد الانتهاء من البرمجة، حان وقت إطلاق التطبيق. في NestJS، الكود المكتوب بـ TypeScript يجب أن يُبنى (Compile) ليتحول إلى JavaScript نقي وسريع يمكن لـ Node.js تشغيله على الـ VPS.

خطوات التحضير وبناء التطبيق (Build):

  1. توليد نسخة الإنتاج (Build): 
    pnpm run build
    هذا الأمر سيقوم بإنشاء مجلد جديد اسمه dist يحتوي على الكود الجاهز للإنتاج. هذا المجلد هو كل ما تحتاجه برمجياً للتشغيل.
  2. تحضير ملف البيئة (.env): ملف .env الحالي يحتوي على روابط التطوير. عند الرفع للـ VPS، ستحتاج لنسخه وتعديله ليحتوي على رابط قاعدة بيانات الإنتاج (PostgreSQL) الخاص بالسيرفر.
  3. تهيئة قاعدة البيانات (Migration): على سيرفر الـ VPS، بعد ربط قاعدة البيانات، قم بتشغيل: 
    npx prisma migrate deploy
    ثم لتوليد الـ Client الخاص بالـ VPS: 
    npx prisma generate

خطوات التشغيل على سيرفر الـ VPS:

بمجرد نقل الملفات (مجلد dist، ملف package.json، ومجلد prisma)، اتبع التالي على السيرفر:

  1. تثبيت الحزم: 
    pnpm install --prod
  2. التشغيل باستمرار باستخدام PM2: أفضل طريقة لتشغيل تطبيقات Node.js على السيرفرات هي استخدام مدير عمليات مثل PM2 ليضمن إعادة تشغيل السيرفر تلقائياً في حال توقفه. 
    # تثبيت PM2 عالمياً
npm install -g pm2

# تشغيل التطبيق
pm2 start dist/main.js --name "solarhub-api"

# حفظ الإعدادات لتعمل مع إعادة تشغيل السيرفر
pm2 save
pm2 startup

استكشاف الأخطاء وإصلاحها (Troubleshooting)

كيفية إيقاف سيرفر يعمل في الخلفية (منفذ مستخدم مسبقاً)

إذا واجهت خطأ يفيد بأن المنفذ قيد الاستخدام بالفعل (مثلاً: listen tcp :8080: bind: address already in use)، فهذا يعني أن هناك نسخة سابقة من السيرفر لا تزال تعمل. يمكنك إيقافها باتباع الخطوات التالية في نظام macOS / Linux:

  1. البحث عن رقم العملية (PID): 
    lsof -i :8080
    هذا الأمر سيقوم بعرض العمليات التي تستخدم المنفذ 8080. ابحث عن الرقم تحت عمود PID.
  2. إنهاء العملية (Kill): 
    kill -9 <PID>
    استبدل <PID> بالرقم الذي وجدته في الخطوة السابقة.
